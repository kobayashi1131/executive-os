## 背景

- 案件の写真は今、各端末の localStorage（`proj_photos_{案件id}`）にしかなく、撮った人の端末でしか見られない
- 以前は「会社用の新しいGoogleアカウント＋写真専用GAS＋Google Drive」で共有する案（A案）で進める予定だった
- 案件データがD1（Cloudflare）に移ったため、写真だけGASを通すと、そこだけ遅い経路が残る（1枚ごとに1.5秒〜数十秒）
- そこで、写真も同じCloudflareに置く方向で見直している。社長は課金を避けたい意向

## 選択肢（無料枠は2026-10時点の把握。実施前に料金ページで確認すること）

| | R2 | KV |
|---|---|---|
| 支払い方法の登録 | 必要（R2の有効化に必要） | 不要 |
| 無料枠 | 保存10GB／書き込み月100万回／読み出し月1000万回／外への転送は無料 | 保存1GB／書き込み1日1,000回／読み出し1日10万回 |
| 無料枠を超えたら | 従量課金（保存は1GBあたり月約0.015ドル） | 無料プランでは書き込みが止まるだけ。請求は来ない |
| 一貫性 | 強い | 結果整合（他の端末に反映されるまで最大60秒ほど） |
| 1ファイルの上限 | 十分大きい | 25MB |

## 容量の見積もり

- アプリは `photos.js` の `resizeImage()` で、写真を長い辺800px・JPEG品質0.72に縮小してから保存する（1枚約100KB）
- 小林のPCにある `Dropbox/カメラアップロード` の実測：約15,200枚・81GB。最近は年約2,000枚撮っている
- 縮小後は年約200MB。R2なら数十年、KVなら約5年もつ
- 縮小しない場合は年約14GBで、KVには入らず、R2は1年以内に無料枠を超える
- → **縮小は今のまま必須にする**

## 社長に判断してもらうこと

**Cloudflareに支払い方法（カード）を登録してよいか**
- よい → R2（推奨。移行の手間が将来も発生しない）
- 避けたい → KV（約5年は0円。一杯に近づいたら整理するかR2に移す）

## 社長にお願いしたい操作（R2に決まった場合のみ）

アカウントの持ち主として、支払い方法の登録とR2の有効化をお願いしたい。小林はメンバーなので、権限の関係で支払いの画面に入れない可能性が高い。

1. Cloudflareのダッシュボード → R2 Object Storage
2. R2の利用開始（Purchase R2 Plan / Get started など、画面の表示に従う）
3. 支払い方法を登録する（無料枠内なら0ドル）

バケットの作成、Pagesへのバインド、再デプロイは、D1のときと同じく小林が行える。

KVに決まった場合、社長の操作は不要。

## 実装の考え方（案。決まってから設計書に起こす）

- 置き場所：R2のバケット（例 `wac-photos`）またはKVのnamespace。Pagesにバインドする（例 `PHOTOS`）
- 窓口：`functions/api/photos.js` を追加する。アップロード・取得・削除を受け付け、今の `/api/projects` と同じ `APP_SECRET` で守る
- 案件との紐づけ：D1にある `projects.photos` 列（カンマ区切り）は使える。ただし、案件全体を保存するたびにこの列が上書きされる。2人が同時に同じ案件へ写真を足すと、片方の写真が消える恐れがある。`photos` テーブルを分ける（photoId, projectId, createdAt, staff, deleted）か、サーバー側で追記する方式が安全
- 二重登録を防ぐ：写真の中身のハッシュ（SHA-256）をキーにして、送り直しても1枚にしかならないようにする
- 表示：詳細画面を開いたときだけ取りに行く。取った写真は端末のIndexedDBに保存して、次からは通信しない。`<img>` はヘッダーを送れないので、`?secret=` を付けるか、fetchで取ってからblobとして表示する
- いたずら対策（特にR2）：1枚の大きさの上限（例 1MB）と、1日の枚数の上限を窓口側で決める
- 移行：各端末の `proj_photos_*` を、新しい置き場所へ自動で送る（全部送れたら元データを消す）
- 範囲外：改善提案の写真（改善提案自体がまだlocalStorageのみ）、v2、「写真」画面の仮の枚数表示

## 進め方の約束
